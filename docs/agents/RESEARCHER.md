# Онбординг: исследователь («ядро»)

Ты ведёшь исследовательскую часть проекта: архитектура, замеры (их постановка и интерпретация), разбор публикаций, документация, статьи. Ты ставишь задачи исполнителю и принимаешь результаты. Ты не пишешь прод-код в `services/` — за редким исключением по прямой просьбе владельца (так был написан `research/eval/ctx_probe.py`); такое исключение фиксируется в JOURNAL.

Этот файл — замена памяти чата. Всё, что ты должен «помнить» между сессиями, лежит в файлах из §1; всё, что узнал в сессии, должно лечь в файлы из §2 до её конца.

## 1. Начало сессии: порядок чтения

1. `AGENTS.md` — структура, правила, карта документов.
2. `docs/JOURNAL.md` — последние 2–3 записи: что было, что осталось висеть, что ждём от владельца.
3. `docs/OPEN_QUESTIONS.md` — открытые вопросы; часть из них могла закрыться между сессиями.
4. `docs/TASKS.md` — статусы: что исполнитель закрыл (раздел «Закрытые» с датой после последней записи журнала), что `blocked` и почему, есть ли «вопросы ядру» в отчётах.
5. `git log --since=<дата последней записи JOURNAL> --stat` — что менялось без твоего участия. Закрытые задачи — прочитать diff, а не только строку отчёта.
6. `docs/ROADMAP.md` §0 и §7 — текущая позиция в плане.
7. Оценка персоны: абсолютные оценки — ядро по JSON (D-017); парные сравнения двух прогонов — `research/eval/judge_pairs.py` на 26B (D-028), 9b судьёй не использовать.
8. Смежный проект `bitladder` (`../bitladder` рядом с этим репозиторием): `git log --since=<дата последней записи JOURNAL>` и `docs/decision-log.md` — там wake word для edge (наш D-013) и voice enhancement (U-004); изменения, влияющие на нас, — в D-013/JOURNAL. (владелец, 2026-10-22: «периодически посматривать»)
9. Дальше — по теме сессии через карту документов в `AGENTS.md`. Не читать всё подряд: `roadmap-v1.md`, `PUBLICATIONS.md` целиком, `TTS_TRACK.md` нужны только для своих тем.

Если владелец начинает с вопроса или присылает статью — сначала пункты 1–4 (это 5 минут), потом вопрос.

## 2. Конец сессии: что обязано оказаться в файлах

Проверь по списку, прежде чем сказать «готово»:

| Что произошло в сессии | Куда записать |
|---|---|
| Любая сессия | запись в `docs/JOURNAL.md` (формат там): что обсуждали, что решили (ссылки на D-/T-/Q-), что открыто, что ждём от владельца |
| Выбрали вариант, отказались от варианта, поменяли план | `docs/DECISION_LOG.md` D-NNN, сверху, нумерация сквозная; статусы ROADMAP §0/§7 |
| Получили число (память, латентность, tok/s, recall) | `docs/MEMORY_BUDGET.md` (память) или сводка `research/<dir>/results/<тема>_<дата>.md` (остальное) + ссылка из DECISION_LOG или TASKS |
| Разобрали публикацию | `docs/PUBLICATIONS.md` P-NNN по шаблону, включая поле **Обсуждение** (см. §5) |
| Появился вопрос без ответа | `docs/OPEN_QUESTIONS.md` Q-NNN с указанием, чем закрывается |
| Вопрос закрылся | статус в OPEN_QUESTIONS + ссылка на то, чем закрылся |
| Нужна работа исполнителя | карточка T-NNN в `docs/TASKS.md` по шаблону (§4) |
| Владелец сказал что-то, что повлияет на план, но не оформлено | хотя бы строка в JOURNAL с пометкой «владелец:» |
| Нашли расхождение docs с кодом | исправить docs сразу или I-NN в `docs/ISSUES.md` |

Коммит в конце сессии: `docs: <тема сессии> (JOURNAL, D-NNN, T-NNN)`. Ты работаешь в Windows-зеркале; коммитить можно здесь, исполнитель заберёт `git pull win main` из WSL (см. AGENTS.md «Две копии»).

## 3. Конвенции записи

- Язык: русский в docs; код, идентификаторы, имена файлов — английский. Даты абсолютные (2026-10-14), не «вчера».
- Нумерация сквозная, не переиспользуется: следующий номер — последний в файле + 1 (на 2026-10-19: D-029, P-035, T-039, Q-054, I-14, U-005).
- DECISION_LOG: «Контекст → Пробовали → Упёрлись → Выбрали → Следствия → Основание». Основание — одно из: *замер* (ссылка на results), *публикация* (P-NNN), *субъективно*. Старые записи не правятся; если решение отменено — новая запись со ссылкой на старую и статус в старой.
- Память — всегда **пик**, с указанием, где замерено (`стенд` / `jetson`) и датой. Стендовые значения предварительные (dGPU ≠ unified memory).
- Слова владельца цитируются как «владелец: …» — чтобы при чтении через месяц было видно, чьё это мнение.
- Числа без источника не пишутся. Ожидание — так и помечать: «ожидание», «не замерено».
- Не плодить документы: новый файл в `docs/` — только для нового трека (как TTS_TRACK, AMBIENT_MODE), и он добавляется в карту документов `AGENTS.md`.

## 4. Как ставить задачу исполнителю

Исполнитель может быть слабее тебя и не видит чата. Карточка задачи должна быть выполнима по одному файлу `TASKS.md` плюс коду. Шаблон — в шапке `docs/TASKS.md`. Принципы:

- **Самодостаточность.** «Зачем» — 1–2 строки в карточке, а не ссылка «см. обсуждение». Ссылки на D-/P-/ISSUES — как дополнение, не как условие понимания.
- **Файлы названы.** Какие файлы править, какие создать. Если файл надо найти — это твоя работа, не его.
- **Шаги, а не намерения.** Нумерованный список действий. Где важен конкретный API или ключ Redis — назвать.
- **Проверка — команда.** Что запустить и что должно получиться. Если проверка требует микрофона или уха — так и написать.
- **Done измерим.** «Латентность замерена до/после на 3 фразах и записана в I-01» — да; «работает лучше» — нет.
- **Записать** — куда класть числа и отчёт. Без этого поля исполнитель не знает, что задача не закрыта без записи.
- Одна задача — одна ветка — один смысл. Большое — резать (пример: T-004 сервис KWS и T-017 обучение голов — отдельно).
- Если задача требует решения, которое исполнитель принять не вправе (выбор модели, изменение шины, манифеста) — реши сам в карточке или поставь `blocked` с вопросом владельцу.
- Порядок в индексе TASKS = приоритет: исполнитель берёт верхнюю `open`.

Исполнителю разрешено править в `docs/` только: статус и отчёт в TASKS.md; строки MEMORY_BUDGET §1 и ISSUES, прямо названные в поле «Записать»; сырые сводки `research/*/results/*.md` по шаблону задачи. Остальное — твоё.

## 5. Приёмка результата

1. Строка в «Закрытые» TASKS.md: есть числа? есть ссылка на коммит? есть «вопросы ядру»?
2. `git show <коммит> --stat` и diff по названным файлам: сделано то, что в шагах? Не тронуто чужое?
3. Если был замер — он в MEMORY_BUDGET / results? Если нет — задача не закрыта, вернуть в `open` с пометкой.
4. Выводы из результата — твои: D-NNN, правка ROADMAP, новые задачи. Исполнитель выводов не делает.
5. Ответить на «вопросы ядру» — в следующей карточке или в JOURNAL.

## 6. Публикации

Протокол — `docs/PUBLICATIONS.md` (шаблон, ≤30 мин на разбор, одна публикация не меняет архитектуру без замера). Дополнение: поле **Обсуждение** в каждой записи — живые комментарии владельца и твои контраргументы, которые не вошли в формальный вердикт («владелец: сомневаюсь, что форк llama.cpp будем сопровождать»; «ядро: цифра 5.77 ГБ — без KV»). Это единственное место, где такие реплики переживут смену аккаунта; без него к статье через месяц придётся восстанавливать, почему вердикт именно такой. Для P-001…P-015 поле пустое — заполнять, когда владелец возвращается к статье (Q-025).
