### P-018 · JEV-35B (AutoTrust) — «решающая» модель: выбор из вариантов за один проход · 2026-10-16
Источник: huggingface.co/autotrust/JEV-35B, карточка и новостные пересказы (hermes-ai.net, alphasignal.ai)  Тип: release + веса (Apache-2.0)
Тезис: дообучение Qwen3.5-35B-A3B (MoE, ~3B активных) в модель «System 1»: не генерирует текст, а за **один forward** выбирает ответ — да/нет, оценка 0–5, выбор из ≤256 вариантов (`/v1/decide`). Медиана 204 мс на B200; NVFP4-вариант 25.6 ГБ. Decision Index 0.3 — 59.73 (self-reported); ERQA 51.3 % без робототехнических данных. Сестринская JEV-27B-VL — с картинками.
Привязка: A-02 (нет: 35B), A-08 (режим B — та же база, что `qwen3.6:35b-a3b` в нашем списке), AMBIENT_MODE (фильтр инициативы), U-002 (классификатор «нужна проверка?»), D-017 (судья).
В чём прелесть (ответ на вопрос владельца): это LLM, превращённая в **классификатор**. Вместо «подумай и напиши» — распределение по заранее заданным вариантам ответа, как у энкодера, но со знаниями и контекстом 35B-модели. Выигрыш: латентность одного прохода вместо генерации, детерминизм, батчинг, калиброванные оценки — ровно то, что нужно судье, роутеру, фильтру и любому «да/нет» в пайплайне. Цена: ничего не объясняет, варианты надо задать заранее.
Проверяемое следствие (≤2 ч, стенд): паттерн переносится на **наш** 4B без дообучения — вероятности первого токена по списку вариантов («0».."5", «да»/«нет») через llama-server (`n_probs`/logprobs; у ollama API logprobs нет — это аргумент за llama-server в манифесте brain). Замер: (1) оценка персоны 13 реплик CTX-1 одним проходом gemma4:e4b-it-qat против chat-судьи — согласие и латентность; (2) фильтр AMBIENT «реагировать?» на 50 фразах. Сама JEV-35B — только как режим B-эксперимент (судья/роутер на стенде, 8 ГБ не влезет).
Вердикт: **модель — отложить до M8b** (класс 35B-A3B, туда же, где qwen3.6); **паттерн «decide за один проход» — принять к проверке** (задача после T-018). Цитировать: статья №2 («LLM как классификатор на edge: судья, фильтр инициативы»).
Заметки: цифры self-reported; «Decision Index» — их собственный бенчмарк. Не путать с закрытой TypeSafe Jev.
Обсуждение: владелец (2026-10-16): «скорее хотелось бы в принципе разобраться, в чём прелесть этих моделей».

### P-016 · Looped/recursive transformers: Nanbeige4.2-3B (2607.22083) и «Loop the Loopies!» (2607.16051) · 2026-10-16
Источник: arxiv 2607.22083 (Nanbeige4.2-3B: Unlocking Agentic Capabilities in a Compact Model; HF Nanbeige/Nanbeige4.2-3B, Apache-2.0); arxiv 2607.16051v2 (Loop the Loopies!, Gao et al.); arxiv 2608.13987 (Nanbeige на Apple Silicon: баги деплоя и память); сводки groundtruth.day, hackernoon, pith.science  Тип: 2 paper + веса
Тезис: один стек слоёв прогоняется дважды — глубина ×2 без новых параметров. **Nanbeige4.2-3B**: 22 слоя ×2 = 44 прохода, 3B non-embedding, 28T токенов с нуля, многоступенчатый RL; заявляют превосходство над Qwen3.5-9B и Gemma4-12B на агентских бенчмарках при конкурентных reasoning/alignment. **Loopies**: рецепт обучения looped-MoE (20B-A2B и 6B-A0.6B, два шага цикла, «layer-level loop»); на HF — «золото IMO/IPhO». Сторонний разбор (pith): сравнение «при том же компьюте» не FLOP-matched. Цена цикла: вычисления на токен ×2, память **весов** ×1 — это компактность за счёт скорости; attention-память на префилле ~×2 (2608.13987), там же 5 багов деплоя в transformers.
Привязка: A-02 (кандидат режима A, текстовый), A-09 (форматы), риск ROADMAP §6 п.2 (устаревание кандидатов), M9 (QLoRA на looped-модели — неизвестно).
Что это значит для 8 ГБ: наш лимит — память, не компьют. Looped 3B = веса ~2 ГБ Q4 при «эффективной» глубине 44 слоя; KV как у 44-слойной (проверить: пишут ли оба прохода свой KV), decode на Orin memory-bound — веса читаются дважды → tok/s как у ~6B dense (ожидание, замерить). Если качество персоны/русского на уровне 9B при памяти 3B — это лучший размен из возможных. Русский в карте не заявлен — отсев первым. Зрения нет → текстовая альтернатива (как ministral/phi4-mini).
Проверяемое следствие (≤2 ч): GGUF есть у сообщества (`ollama run hf.co/owao/Nanbeige4.2-3B-GGUF:Q4_K_M`, 2.57 ГБ; bartowski, Abiray); официальный путь — форк ollama `nanbeige42`. Риск: looped-архитектура в stock llama.cpp — одна из сборок (Andgihat) предупреждает, что не запустится; проверить на owao. Замер: bench_vlm_mem (пик, tok/s, KV-рост 2k→16k — главный вопрос) + CTX-1 (русский, персона, math) + JSON/tool-calling, раз модель «агентская».
Вердикт: **принять в матрицу M5 как текстового кандидата** (строка в MEMORY_BUDGET §3), с отсевом по русскому; Loopies — **отложить** (веса 6B-A0.6B для CPU-инференса были бы интересны — проверить, выложены ли; идея «MoE с 0.6B активных на CPU» = голосовой тракт без GPU). Цитировать: статья №1 («что влезает»: looped как ось «память vs компьют»), статья №2.
Заметки: Nanbeige4.5 (LoopSplit, mHC, n-gram embeddings) в обучении — следить. Для Orin: compute ×2 при CPU A78AE — если модель пойдёт на CPU, не пойдёт; только GPU.
Обсуждение: владелец прислал как «рекурсивные трансформеры» (2026-10-16); первая ссылка — не обзорная статья, а конкретная модель на этой идее, что для нас полезнее.

### P-015 · Uzu (Mirai) — ускорение локальных LLM на Apple M5 · 2026-10-10
Источник: uproger.com/uzu-uskorenie-lokalnyh-llm-apple-m5 (пересказ); github.com/trymirai/uzu (MIT); блоги Mirai  Тип: blog + repo
Тезис: собственный движок (Metal + CPU, свой формат моделей через `lalamo`). Qwen 3.5 9B на M5 16 ГБ: **22 tok/s у llama.cpp → 92–117 tok/s у Uzu**, префилл ~161 tok/s, TTFT 0.12 с, **5.77 ГБ памяти**. Два источника ускорения: (1) int4 асимметричная квантизация с блочно-диагональным преобразованием Адамара до квантизации (перераспределение выбросов) + int8-пути M5; (2) **спекулятивное декодирование**: параллельный драфт до 16 токенов, адаптер «Weaver» на 56.7M параметров отбирает кандидатов последовательно, древовидная верификация без отката состояния; 8–16 токенов за forward. На M1–M4 работает без спекуляции. Linux ARM — «в работе», только CPU-бэкенд; CUDA нет.
Привязка: A-03 (рантайм), A-08 (B-lite), A-09 (форматы), M8b, M9 («опционально спекулятивное декодирование»).
Что нового относительно партии 1: спекулятивное декодирование — единственная техника, которой в разобранных работах не было; остальное (Адамар перед низкобитной квантизацией) — та же семья, что складки Адамара у Bonsai 2 (P-012).
Проверяемое следствие (стенд → Orin): для B-lite (dense 8–9B Q4, декод упирается в полосу памяти: Orin ~102 ГБ/с против ~150 у M5) — llama.cpp с драфт-моделью того же семейства (Qwen3.5-0.8B Q8, ~0.6–1 ГБ с KV): tok/s без/с драфтом, доля принятых токенов на репликах персоны (стиль персоны может снижать acceptance у стокового драфта), прирост памяти. Гейт: ≥1.5× tok/s при сохранении бюджета режима B. Для режима A (4B) выигрыш ожидается меньше, TTFT важнее — проверять вторым.
Вердикт: **движок — отклонить** (Metal/Apple, свой формат, CUDA нет); **технику спекулятивного декодирования — перенести из «опционально» в M9 в обязательный замер bake-off M8b** для B-lite. Калибровочная цифра: 9B int4 целиком с KV = 5.77 ГБ — верхняя граница B-lite в наш бюджет 8 ГБ влезает только без YOLO и с CPU-голосом. Цитировать: статья №2 (спекуляция на edge и почему легковесные головы класса Weaver/EAGLE нам недоступны без обучения).
Заметки: Weaver — обученная голова, как EAGLE/Medusa; в llama.cpp нативно нет, есть классический драфт отдельной моделью и n-gram lookup (бесполезен для свободного диалога). **Дополнение 2026-10-13:** в библиотеке ollama есть теги `-mtp-q4` (multi-token prediction, встроенные головы спекуляции) у `gemma4:26b-a4b-it-mtp-q4` и `qwen3.6:35b-a3b-mtp-q4` — это спекулятивное декодирование без драфт-модели и без лишней памяти, ровно для режима B. Для 4B/9B тегов mtp в регистре пока нет (9b-mtp-q4 — manifest unknown). Замер в M8b: tok/s q4 vs mtp-q4 на стриминге экспертов.

### P-014 · EmbeddingGemma 2 — мультимодальный эмбеддер 740M для on-device · 2026-10-07
Источник: blog.google/.../embeddinggemma-2; модельная карта HF  Тип: release + веса (Apache-2.0)
Тезис: модульная модель на архитектуре Gemma 4: **270M текст** + опционально 170M vision + 300M audio = 740M; текст, код, изображения, видео, аудио в одном пространстве 768-d, Matryoshka до 512/256/128. Контекст 8k токенов (≈5.5 мин аудио / 29 изображений). RAM квантованной: **~191 МБ текст-only, ~567 МБ полная**. 100+ языков; MTEB multilingual v2 61.36 (на уровне EmbeddingGemma 1), MTEB Code 78.68, MMEB v2 image retrieval 57.28, MSEB sound retrieval 69.54. Рантаймы: llama.cpp, Ollama, sentence-transformers ≥6.1, LiteRT, ONNX/transformers.js.
