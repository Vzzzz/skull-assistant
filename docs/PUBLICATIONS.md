### P-014 · EmbeddingGemma 2 — мультимодальный эмбеддер 740M для on-device · 2026-10-07
Источник: blog.google/.../embeddinggemma-2; модельная карта HF  Тип: release + веса (Apache-2.0)
Тезис: модульная модель на архитектуре Gemma 4: **270M текст** + опционально 170M vision + 300M audio = 740M; текст, код, изображения, видео, аудио в одном пространстве 768-d, Matryoshka до 512/256/128. Контекст 8k токенов (≈5.5 мин аудио / 29 изображений). RAM квантованной: **~191 МБ текст-only, ~567 МБ полная**. 100+ языков; MTEB multilingual v2 61.36 (на уровне EmbeddingGemma 1), MTEB Code 78.68, MMEB v2 image retrieval 57.28, MSEB sound retrieval 69.54. Рантаймы: llama.cpp, Ollama, sentence-transformers ≥6.1, LiteRT, ONNX/transformers.js.
Привязка: A-13 (память: эмбеддер), M10, частично M7 (кадры).
Проверяемое следствие (≤2 ч, стенд): (1) текстовая часть через llama.cpp на CPU: RSS, мс на запрос из 50 токенов, качество recall на 30–50 русских «запомни/вспомни» парах против multilingual-MiniLM (кандидат v1); (2) полная модель на CPU: RSS и мс на кадр 640×480 — можно ли индексировать кадры с YOLO-событий без GPU.
Вердикт: **принять как основного кандидата эмбеддера M10** вместо multilingual-MiniLM — при 191 МБ и CPU-инференсе проходит бюджет голосового стека; снимает возражение против P-006 (там 2B и GPU). Полная мультимодальная версия — опционально для M7/M10: индекс кадров и звуков комнаты в том же пространстве, что и текст памяти, без второй VLM-размерной модели. Записать D-NNN после замера.
Заметки: MTEB multilingual не вырос относительно v1 — для русского текста выигрыш не в качестве, а в том, что один эмбеддер покрывает и кадры, и аудио-события; русский проверить на своих данных, бенчмарка ruMTEB по модели нет. На Jetson — CPU-only через llama.cpp/ONNX, чтобы не плодить CUDA-контексты.

Тезис: KWS «быстрых команд» (дальше/тише) отдельно от wake word, модели **0.5–1.5 МБ** на устройстве. Данные: предобучение на 60–100 млн неразмеченных фрагментов из ASR-логов, дообучение на 400k–1M записей из домашних условий (писали вручную — артефакты близости к wake word иначе портят домен). Новые команды — замороженная база + ветка ≤10k параметров с отдельной головой: FRR 6.46→4.37 %, ложные срабатывания −60 %, CPU −35 %, RAM −50 %.
Привязка: A-04, A-10 (barge-in через KWS), M4-доделка, ISSUES I-10.
Проверяемое следствие: openWakeWord уже устроен модульно (общий melspec+embedding, маленький классификатор на слово) — обучить 2–3 головы («стоп», «тише», «дальше») на синтетике (Piper) и замерить FA/FR в комнате; затем сравнить с добавкой 50–100 реальных записей.
Вердикт: **принять как дизайн-референс KWS-сервиса**: отдельный сервис, общая feature-часть с wake word, по голове на команду, резидентен во всех режимах (`never_evict`). Цитировать: статья №1.
Заметки: их главный урок — данные из домена комнаты важнее архитектуры; синтетика — старт, не финиш.
