# Skull Assistant — Roadmap v2

Реорганизация от 2026-09-24. Исходный план (v1) — `docs/roadmap-v1.md`, архитектурные решения из него остаются в силе и здесь не переписываются, только дополняются.

Голосовой ассистент с характером в корпусе анатомического черепа **и** платформа для запуска компактных ML-сервисов на одном edge-устройстве.
Платформа: Jetson Orin Nano Super 8GB. Стенд: RTX 3080 Laptop 8GB, WSL2. Темп: ~20 ч/нед, коэффициент запаса ×1.3.

**Фактическая реализация (осмотр WSL Ubuntu-22.04, `~/skull-assistant`, 2026-09-29):** пять user-юнитов systemd (`skull-capture/wakeword/stt/brain/tts`), 188 строк python, шина Redis Streams (`audio:mic` кольцо 60 с по 30 мс кадрам → `events:wakeword` → `events:transcript` → `events:reply`). В ollama лежат gemma3:4b (3.3 ГБ), gemma4:e2b (7.2 ГБ), gemma4:e4b (9.6 ГБ) — все Q4_K_M.

Линейный список milestones v1 перегруппирован по трём результатам. Каждый milestone работает минимум на один из них; портфолио-пороги — точки, где результат демонстрируем.

## 2. Дополнение к архитектуре: контракт сервиса платформы

Каждый ML-сервис (уже существующие M1–M4 тоже, ретроспективно) описывается манифестом. Диспетчер M8 читает манифесты, а не хардкод.

```yaml
# services/<name>/manifest.yaml
name: vlm-main
unit: skull-vlm.service            # systemd-юнит
backend: llama.cpp                 # llama.cpp | pytorch | tensorrt | cpu
cuda_context: true                 # создаёт ли CUDA-контекст
budget:                            # ПИКИ из MEMORY_BUDGET.md, не установившиеся
  vram_mb: 3900
  ram_mb: 1200
  measured_on: jetson | stand      # где замерено; stand-значения — предварительные
residency:                         # в каких режимах резидентен
  A: resident
  B: evacuated
  C: evacuated
lifecycle:
  freeze: slot-save-kill | serialize-kill | kill
  thaw: start-slot-restore | start-restore-queue | start
  thaw_budget_s: 10
bus:
  in:  [stt.final, vision.event]
  out: [vlm.reply.stream, vlm.tool_call]
healthcheck: http://127.0.0.1:8081/health
never_evict: false                 # true только у KWS/wake word
```

Правила: `never_evict` ровно у одного сервиса (KWS); сумма `vram_mb` резидентов режима + резерв под KV ≤ бюджет режима; манифест без `measured_on` не допускается диспетчером в admission control.

Done-критерий контракта (закрывается внутри M8): все сервисы M1–M7 имеют манифесты, диспетчер стартует режим A только из них.

## 3. Остаток плана

### Ветка А (выбрана 2026-09-29): устройство есть

Порядок: **долг Фазы 0 (git, бюджеты по стенду) → M5 на устройстве → M4-доделка на устройстве → TTS-трек → M6/M7 → 🏁2.**

Почему M4 доделывать *после* M5, а не до: стриминговая склейка, barge-in и выбор TTS зависят от реальных латентностей на Orin (CPU A78AE медленнее 5800HS в 2–3 раза на поток); на стенде их не откалибровать. M5 даёт цифры, M4-доделка их использует. Исключение — стрим `stream: True` в brain и разрезка по предложениям: это переносимая логика, можно сделать на стенде в будни.

Параллельно в будни: датасет персоны (M9), TTS-датасет для своего голоса (TTS_TRACK.md), манифесты.

Наша часть: `services/wake_bridge` (MCU→`events:wakeword`), устойчивость юнитов к SC7 resume (USB re-enumerate, CUDA), замер «импульс → Jetson слушает», маскировка. ## 4. Трек публикаций (R3)

### 4.1 Входящие публикации — протокол разбора

Владелец периодически присылает статьи/репозитории/бенчмарки. Каждая проходит через `PUBLICATIONS.md` по одному шаблону (там же). Суть протокола:

1. **Тезис** в 2–3 строках — что утверждают и на чём измерено.
2. **Привязка** — к какому решению архитектуры или milestone относится (таблица решений в PUBLICATIONS.md).
3. **Проверяемое следствие** — что именно можно перемерить у себя за ≤2 ч. Если такого нет — публикация только для обзора литературы.
4. **Вердикт**: *принять* (меняем план/архитектуру → запись в DECISION_LOG), *отложить* (до конкретного milestone), *отклонить* (почему), *цитировать* (глава статьи).
5. Правило: одна публикация не меняет архитектурное решение без замера. Замер — да.
