# Трек TTS: качество, свой голос, диалоговый режим

Открыт 2026-09-29. Три задачи в одном тракте: (1) поднять качество синтеза, (2) заменить стоковый голос на голос «под сеттинг», (3) сделать TTS пригодным для диалогового режима (стриминг, прерывание), а не только для «wake word → одна реплика».

---

## 1. Ресурсная рамка (что можно потратить на TTS на Orin 8 ГБ)

Из архитектуры v1: звуковой тракт **CPU-only, ноль CUDA-контекстов**, весь голос (KWS + STT + TTS) ≈ 0.7–1 ГБ RAM. На TTS из этого разумно ≤ 300–400 МБ RSS. Причина жёсткости: каждый CUDA-контекст на Orin — сотни МБ из тех же 8 ГБ, что и у VLM; VLM 4B Q4 + KV ≈ 3.5–4.5 ГБ, плюс Whisper, плюс YOLO. Резерв под TTS на GPU не появится.

Скоростные требования (RT-фактор = время синтеза / длительность аудио):
- Режим A, диалог: первое аудио ≤ ~300–500 мс после первого предложения от VLM; RT ≤ 0.3 на Orin, чтобы синтез следующего предложения успевал за проигрыванием текущего. Orin CPU (6× A78AE ~1.5 ГГц) медленнее 5800HS на поток в ~2–3 раза → **на стенде целиться в RT ≤ 0.1–0.15**, финальный замер — только на устройстве.
- Режимы B/C: скорость не критична, но GPU занят стримингом экспертов — TTS всё равно CPU.

Вывод: GPU-класс TTS (клонирование голоса, диффузионные/LLM-модели) в основной контур не проходит **по архитектуре, а не по качеству**. Его место — офлайн, см. §3.

## 3. Рецепт «свой голос» без GPU в рантайме — дистилляция

Идея: тяжёлая клонирующая модель работает **один раз, офлайн, на ноутбуке**, лёгкая — в рантайме.

1. Выбрать целевой тембр (образец 10–30 с: актёр, свой голос с обработкой, синтетический).
2. Офлайн на RTX 3080: клонирующей моделью (XTTS-v2 / F5-TTS-ru / Fish) синтезировать **датасет 1–3 тыс. фраз в целевом голосе** — тексты берём из датасета персоны M9 (двойная польза) + нейтральные предложения для покрытия фонетики. Прослушать, выкинуть брак.
3. Дообучить Piper-чекпойнт `ru_RU-*-medium` на этом датасете (fine-tune, не с нуля; часы на 3080 laptop).
4. Экспорт onnx → тот же `speaker.py`, RT и RSS не меняются.
5. Альтернатива на шаге 2–3: Piper + RVC (§2), если дообучение Piper даст артефакты — но это плюс модель в рантайме.

Побочный выигрыш: **фиксированные фразы персоны** (реплики перехода режимов «дай подумаю», приветствия, реакции на YOLO-триггеры) можно отрендерить офлайн лучшей моделью и хранить wav — качество максимальное, стоимость в рантайме нулевая. Голос совпадает с рантаймовым, потому что Piper дистиллирован из той же модели.

Эффекты: текущая цепочка sox `pitch −300` + reverb — pitch-shift сдвигает форманты и даёт металлический артефакт. С дообученным низким голосом сдвиг не нужен; оставить только «акустику черепа» — короткий reverb + резонансный EQ (полость ~ 300–600 Гц). Замерить, что sox не съедает латентность (сейчас три файла в /tmp последовательно).

## 4. Диалоговый режим — что TTS должен уметь

Сейчас: brain отдаёт весь ответ (`stream: False`) → TTS синтезирует весь текст в файл → sox → paplay. Латентность «конец фразы → начало ответа» = полная генерация VLM + полный синтез. Для диалога нужно:

1. **Стрим от VLM** (`stream: True`) + разрезка по предложениям на стороне brain → `events:reply` получает предложения по одному. Переносимая логика, делать на стенде. Замер T2 подтвердил необходимость: Piper не стримит внутри предложения, первое аудио = полный синтез первого предложения, поэтому короткое первое предложение = короткая латентность (TASKS T-003).
2. **Очередь синтеза** в TTS: синтез N+1 во время проигрывания N; проигрывание через `sounddevice`/pyaudio поток чанками, а не `paplay` файла — иначе нечего прерывать.
3. **Прерывание**: команда `tts:stop` из KWS-сервиса → сброс очереди и остановка потока за ≤ 100 мс. Это и есть barge-in из M4.
4. **Самоэхо**: в диалоговом режиме микрофон открыт во время речи. Решение (bitladder/docs/hardware.md, D-013): **аппаратный AEC в микрофонном модуле — ReSpeaker Lite** (XMOS XU316; микрофоны и динамик на одном устройстве, иначе AEC не работает; проверить выход на динамик у версии). Полудуплекс с KWS остаётся fallback на стенде и без модуля; программный AEC (webrtc/speexdsp) — запасной вариант.
5. **Статус на шине**: `tts:speaking` уже есть; добавить `tts:until_ts`, чтобы STT/VAD знали, когда ждать хвост реверберации.

Замеры для этого раздела: латентность первого аудио на стенде и на Orin для Piper и для финалиста бейк-оффа; время реакции на `tts:stop`.

## 6. Интонация и поток против CUDA-контекстов (добавлено 2026-10-07)

Выразительные LLM-based TTS (Fish/OpenAudio S1-mini, Chatterbox, Orpheus, CSM; 0.5–3B) в режиме A при текущей раскладке не помещаются: контекст + 1–3 ГБ весов рядом с VLM и YOLO. Три пути, все замеряются в T3:

| Конфигурация | GPU-контексты в режиме A | Что даёт | Цена | Замер |
|---|---|---|---|---|
| **Регистры в Piper (база)** | 2 (VLM, YOLO) | multi-speaker Piper, где «спикеры» = регистры одного голоса (нейтральный / ироничный / усталый / резкий); VLM метит предложение тегом; noise_scale/length_scale на предложение | ограниченный потолок выразительности; нужен датасет по регистрам (тот же офлайн-учитель, §3) | слепое сравнение на 15 репликах с тегами |
| **YOLO → CPU, GPU-слот под TTS** | 2 (VLM, TTS) | TTS 0.5B класса с кастомным голосом и контекстной интонацией | fps детектора (нужно ≥2–5 fps на 320px для триггера присутствия); RSS детектора на CPU | fps и RSS YOLOv8n на CPU Orin; RT/латентность TTS на GPU; суммарный бюджет A |
| **TTS внутри llama-server с VLM** | 2 (VLM+TTS в одном процессе, YOLO) | общий контекст, надбавки нет; кандидаты — OuteTTS-семейство (0.6–1B, русский заявлен) через multi-model режим llama-server | freeze через kill не точечный: TTS гибнет вместе с VLM при смене режима (в B/C голос и так на Piper — потеря мала); качество русского OuteTTS не проверено | работает ли multi-model в целевой версии llama.cpp на Orin; RT, первое аудио, русский |

Во всех трёх случаях фиксированные фразы персоны рендерятся офлайн лучшей моделью (§3). Регистры Piper делаются в любом случае — это голос режимов B и C.

Для статьи №1: таблица «качество речи × число контекстов × fps зрения на одном бюджете 8 ГБ» — развилка, которой нет в соседних публикациях.

## 8. Выбор голоса и пост-обработка (2026-10-22)

**Дополнение 2026-10-31 (владелец):** идеальный голос ассистента — дубляж персонажа из Warcraft 3; это голос актёра и запись Blizzard, **клон для публикации (репо, HF, статья) не годится** — право на голос и на фонограмму. Три пути: (1) **дома** — клон по 30 с образца (XTTS/F5/Fish, §3) только для личного устройства, в репо не кладётся и в статье не упоминается как источник; (2) **публикуемый** — голос «в духе» по текстовому описанию через Qwen3-TTS-12Hz-1.7B-VoiceDesign (уже в `models/hf`): тембр, манера, «нежить с эхом» — без образца реального актёра, затем дистилляция в Piper (§3); отбор на слух владельцем парно против ryan+fx; (3) sox/fx поверх любого из них — как сейчас (pitch −300, reverb). Для портфолио показываем (2); (1) — личный пресет вне git. Связь: U-006 нет; T-013; D-013.

**Вердикт владельца по T-013 шаг 1 (прослушивание `ryan` / `serena`, Qwen3-TTS 0.6B Q4_K_M, GPU):** «очень нравится качество ryan — и по репликам, и по интонациям; не идеал, но для перспективного голосового ассистента именно то, что нужно». `serena` — «так же прекрасна», но не та персона; **оставить как опцию**: характер ассистента резко меняется при тех же репликах (регистры §6 можно делать сменой голоса, а не только промптом). Впечатление «GPU рендерит качественнее CPU» — проверено: wav CPU и GPU при одном seed **не совпадают** (разная длина, корреляция ≈ 0) — бэкенды дают разные числа, сэмплирование расходится, это другой прогон, а не другое качество; воспроизводимость только внутри одного бэкенда.

**Пост-обработка «характер черепа»** (совет со стороны: дисторшн + вокодер): `research/tts/fx.py` (numpy + scipy) — пресеты `radio` (полоса 300–3400 + перегруз + шум), `distortion` (мягкий клип), `vocoder` (канальный вокодер, пила 95 Гц + шум, 15 % сухого голоса), `robot` (вокодер + радиополоса + перегруз), `hollow` (комб-резонанс + короткая комната — «пластиковая полость»). Сэмплы: `research/tts/results/qwentts_listen/fx/<пресет>/{1,7,10,14}.wav` (не в git). Стоимость в проде — миллисекунды на CPU, сервис tts; решение по пресету — владелец на слух; дальше — параметры пресета в манифесте tts и регистры по тегу VLM (§6).
