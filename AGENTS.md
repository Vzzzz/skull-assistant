# skull-assistant: контекст для агентов

Первый файл, который читает любой агент — независимо от инструмента (Claude Code подключает его через `CLAUDE.md`, другие инструменты читают напрямую). Его достаточно, чтобы начать без истории чатов. **Всё, что знает проект, лежит в репозитории; чат и память инструмента — не хранилище.**

## Что это

Главный проект портфолио Валерия: офлайн голосовой ассистент с характером (**Костян**, анатомический череп) на Jetson Orin Nano Super 8 GB — и платформа для запуска компактных ML-сервисов на одном устройстве. Три результата: R1 устройство, R2 платформа (диспетчер режимов A/B/C, манифесты сервисов), R3 публикации на Хабре. Смежный проект: `bitladder` (`../bitladder` рядом с этим репозиторием) — квантование до 1 бита и wake-word триггер на MCU, который будит спящий Jetson (D-013); выжимка всего, что нужно отсюда, — в `docs/DECISION_LOG.md` D-013.

Текущее состояние, следующий этап и очередь — не здесь, а в `docs/JOURNAL.md` (последняя запись) и `docs/TASKS.md`. Этот файл меняется редко.

## Роли: кто ты

Две роли, у каждой свой онбординг. Определи роль и прочитай свой файл **до любой другой работы**:

| Роль | Когда | Онбординг |
|---|---|---|
| **Исследователь** («ядро») | сессия планирования: архитектура, разбор публикаций, docs, постановка задач, приёмка результатов, подготовка статей | `docs/agents/RESEARCHER.md` |
| **Исполнитель** | сессия в WSL (VS Code + агент): код, отладка, замеры по задачам из `docs/TASKS.md` | `docs/agents/EXECUTOR.md` |

Если роль не названа: дали задачу T-NNN или просят править код — исполнитель; обсуждают план, публикации, решения — исследователь. Сомневаешься — спроси одним вопросом.

Единственный канал между ролями — git: `docs/TASKS.md` (задачи и отчёты), `docs/JOURNAL.md` (журнал сессий ядра), коммиты. Memory-функции инструментов не используются: при смене аккаунта или агента они исчезают.

## Смена инструмента или модели

Проект не зависит от конкретного кодового ассистента: всё состояние — в файлах репозитория, протоколы ролей — в `docs/agents/`, задачи и отчёты — в `docs/TASKS.md`, журнал — в `docs/JOURNAL.md`; память инструментов не используется. Обёртки для инструментов — одна строка подключения этого файла (`CLAUDE.md` для Claude Code, `GEMINI.md` для Gemini CLI; Codex, Cursor и другие читают `AGENTS.md` напрямую). Новый ассистент в любой роли начинает с этого файла и своего онбординга — больше ничего не нужно.

Что всё-таки зависит от модели и как с этим работать при смене:
1. **Оценка персоны по D-017** — её ставит «ядро» (модель исследователя) по JSON прогонов CTX-1. Другая модель даст другую шкалу. Калибровка: 9 пар прогонов с известными вердиктами ядра (D-028, `research/eval/results/judge_pairs_2026-10-23_*.md`) — новое ядро сначала оценивает их вслепую и сравнивает; при расхождении ≥ 3 из 9 — записать новую шкалу в DECISION_LOG, не переоценивая старые сводки. Запасной судья без участия ядра — 26B по матожиданию логпробов (`judge_pairs.py --expect-score`, D-028).
2. **Стиль карточек и ответов ядра** — задан примерами в TASKS (шаблон карточки, строки «Принято ядром», «Закрытые») и `docs/agents/RESEARCHER.md` §5; новый ассистент воспроизводит его по образцам, а не по памяти.
3. **Исполнитель** — любая модель, которая умеет работать в WSL по `docs/agents/EXECUTOR.md`; режим двух сессий (ядро на зеркале, исполнитель в WSL) удобен, но не обязателен: одна сессия может делать обе роли по очереди, если явно называет роль.

## Структура

```
AGENTS.md          этот файл; CLAUDE.md — обёртка для Claude Code
services/<name>/   прод: код + manifest.yaml (бюджет по пикам, резидентность A/B/C, freeze/thaw, топики)
core/              общий код; диспетчер появится в M8
deploy/systemd/    skull.target + юниты (@REPO@), install.sh, drop-in ollama; deploy/stand/ — запуск стенда из Git Bash; fetch_models.sh — кандидаты
research/          bench/ (замеры), eval/ (оценочный набор, CTX-1), memory/ (прототип памяти и роутера), tts/ — ничего отсюда не запускается юнитом; results/ — CSV/JSON + сводки .md
docs/              JOURNAL (журнал сессий), TASKS (очередь), OPEN_QUESTIONS (открытые вопросы), ROADMAP, DECISION_LOG, MEMORY_BUDGET,
                   PUBLICATIONS, ISSUES, UX_BACKLOG, TTS_TRACK, AMBIENT_MODE, COGNITION_4B, MEMORY_TRACK, JETSON_BRINGUP, roadmap-v1; agents/ — онбординг ролей
persona/           system_prompt.md; dataset/ приватный (не в git)
models/            веса (не в git) + README с источниками
```

## Архитектура в три строки

Шина: Redis Streams `audio:mic` → `events:wakeword` → `events:transcript` → `events:reply`; флаг `tts:speaking`. Каждый сервис — отдельный systemd user-юнит (`skull-capture/wakeword/stt/brain/tts`, всё — `skull.target`); изоляция процессов = механизм свопа моделей (память GPU возвращается только со смертью процесса). Голосовой тракт CPU-only (триггер по речи Silero VAD, GigaAM v3 STT + voice id CAM++ через sherpa-onnx, Piper со стримом по предложениям; openWakeWord — fallback); VLM — Gemma 4 E4B (своя квантизация IQ4_XS) на llama-server, num_ctx 8192 (D-016, D-023, D-024); фоновый режим и камера — `skull-wakeword` (`trigger: speech`), `skull-vision` (D-029, T-031).

## Правила (общие для ролей)

- **Docs и decision-log на русском**; код, идентификаторы и комментарии в коде — на английском.
- Любое архитектурное решение — запись в `docs/DECISION_LOG.md` («пробовали → упёрлись → выбрали», основание: замер / публикация / субъективно). Старые записи не правятся — меняют статус.
- Бюджеты памяти — **пики**, не установившиеся значения; три точки на сервис (без модели / загружена / после freeze). Запись в `docs/MEMORY_BUDGET.md` обязательна при каждом замере. Замер без записи считается не сделанным.
- GPU получают только сервисы с тяжёлыми вычислениями (VLM, детектор). Голосовой стек и эмбеддер — CPU-only: каждый CUDA-контекст стоит сотни МБ из тех же 8 ГБ.
- Инвариант: wake word/KWS не выгружается никогда (с D-013 переезжает на MCU, на Jetson остаётся fallback).
- Публикации разбираются по протоколу `docs/PUBLICATIONS.md`; архитектура меняется только после замера.
- Сказанное в чате и влияющее на план должно оказаться в файле до конца сессии. Иначе оно потеряно.
- Основная консоль пользователя на Windows — **Git Bash**, не PowerShell. Рабочее железо (4090) и рабочие данные в проекте не участвуют.

## Две копии репозитория и стенд

Рабочая копия — WSL Ubuntu-22.04 `~/skull-assistant` (здесь .venv, модели, юниты, сырые результаты). Зеркало — `C:/Users/<user>/git/skull-assistant` на Windows (здесь работает исследователь). С 2026-10-16 источник правды — **приватный GitHub `Vzzzz/skull-assistant`**: у обеих копий `origin` → GitHub; в зеркале дополнительно remote `wsl` (локальный путь WSL), в WSL — `win` (зеркало). Поток: коммит в любой копии → `git push origin main` → в другой `git pull --ff-only origin main`. История переписана 2026-10-16 (авторство на личную почту); `deploy/sync-win.sh` удалён 2026-10-24 (синхронизация только через GitHub), после Q-032 копия в Windows может быть убрана.

Стенд: RTX 3080 Laptop 8 ГБ в WSL2. При старте WSL `skull.target` поднимается сам (микрофон, wake word, STT, ollama, TTS). **Сервисный режим** (без сервисов и ollama — для загрузки моделей и замеров) — флаг `$HOME/.skull-maintenance` на Windows-стороне, из Git Bash: `deploy/stand/skull-stand.sh service|normal|status|stop` (D-014). Перед действием, которое не должно слышать микрофон или занимать GPU, — `skull-stand.sh status`.
